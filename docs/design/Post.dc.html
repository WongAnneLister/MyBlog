Why Does Your AI Agent Send the Same Email Twice?

Oct 17, 2026 · 8 min read · Agents
English 中文

I once built an agent whose tools included sending quote emails to customers. One day, right after the agent sent an email but before it could record "sent," the system restarted. After the restart, the agent had no idea the email had already gone out, so it sent it again.

The problem isn't the LLM. An LLM is stateless; it can only decide based on its messages. The crash happened exactly between "the email was sent" and "the result was written back to messages." The real problem is that the side effect had already happened, but the system never recorded it.

Borrowing from payment systems

Payment systems ran into this long ago. Before calling the provider, generate an idempotency key and write it with a PENDING status. Call the API with that key, and on success update it to SUCCEEDED.

For agents, you can't use tool_call_id as the key, because it's freshly generated on every inference. Use a key the program owns instead:

idempotency_key = f"{run_id}:{step}:{index}"

Anything that must stay the same across restarts cannot be generated by the LLM.

With a stable key, give the agent a ledger. Before every tool call with side effects, look the key up:

no record First execution. Write PENDING, call the tool, then mark SUCCEEDED and store the result.
SUCCEEDED Already happened. Skip the call and return the stored result. The LLM never notices the restart.
PENDING Crashed mid-call. Reconcile with the email service, or retry with the same key; otherwise flag for human review.

Agent reliability doesn't live in the model. It lives in the harness.
